# 数字孪生模型层说明（物模型 / 机理模型 / 仿真引擎）

> 目录：`backend/app/domain/`（物模型）、`backend/app/simulation/`（机理模型与引擎）、`backend/tests/`（验证）

本文档说明这次改造把系统从"**看起来像孪生的可视化大屏**"推进到"**数据层自洽、有机理模型的孪生原型**"的过程，
以及仍然没有做的部分。面试时可以直接照着讲。

## 1. 改造前后对照（为什么要做这件事）

| 维度 | 改造前 | 改造后 |
| :--- | :--- | :--- |
| 全站功率 | `total_power` 独立随机游走 | 由拓扑潮流算出：Σ 主变承担负荷 × 功率因数 |
| 全站电流 | `current_a` 是**从不更新的常量 472.4A** | `I = S / (√3 · U)`，与功率严格对应 |
| 分闸的影响 | 只改一个内存字段，遥测不受影响 | 拓扑变化 → 潮流重算 → 电流/负载率/温度连锁变化 |
| 变压器温度 | 故障注入直接 `oil_temp = 91.5` 赋值 | IEC 60076-7 一阶热路模型，由负载率与冷却能力演化 |
| 热力图 | 伪彩色 + 位置启发式，与温度无因果关系 | 着色依据模型算出的真实温度场 |
| 健康度 | 写死 96 / 98 / 95 | 由温升、局放、振动、SF6、磨损、动作次数加权计算 |
| 告警 | 硬编码文案 | 物模型阈值**边沿触发**，越限自动生成 |
| 点位定义 | 硬编码在 `devices.py` / `opcua/server.py` 两处 | 统一由 `device_model.json` 驱动，改配置不改代码 |
| 前后端状态同步 | 后端推 snake_case，前端读 camelCase，**多数测点根本没更新** | 显式字段映射表，闭环真正闭合 |
| 测试 | 无 | 51 个用例覆盖一致性、热模型、潮流、引擎 |

**最能说明问题的一条**：改造前 `gis-201` 进线电流 472.4A，而两台主变电流之和 546.2+521.0=1067.2A
——单电源站里进线电流不可能只有主变电流之和的 44%。这个物理矛盾在新模型里被自动消除。

├── simulation/

## 3. 机理模型细节

### 3.1 变压器热路模型（IEC 60076-7 一阶形式）

顶层油温稳态温升与绕组热点温升按负载导则计算，暂态用一阶惯性演化：

```
Δθ_oil(K) = Δθ_oil,rated · ((1 + R·K²) / (1 + R))^x      # 顶层油温升
Δθ_hs(K)  = Δθ_hs,rated · K^y                            # 热点对油温升
θ_hs      = θ_ambient + Δθ_oil + Δθ_hs                   # 绕组热点温度
dθ/dt     = (θ_∞ − θ) / τ                                # 一阶惯性
```

| 参数 | 取值 | 说明 |
| :--- | :--- | :--- |
| `loss_ratio_r` | 6.0 | 额定负载损耗 / 空载损耗 |
| `oil_exponent_x` | 0.9 | 油指数（ODAF 强迫导向油循环） |
| `winding_exponent_y` | 1.6 | 绕组指数 |
| `top_oil_rise_rated_k` | 50.0 / 46.0 | 1#/2# 主变额定顶层油温升（2# 单独覆盖，两台不会算出完全相同的结果） |
| `hot_spot_gradient_rated_k` | 16.0 / 15.6 | 额定热点温升 |
| `τ_oil_real` | 9000 s（2.5 h） | 真实顶层油温时间常数 |
| `τ_winding_real` | 600 s | 真实绕组时间常数 |

**数值自证**：76.1% 负载、冷却正常时，模型稳态给出油温 **58.2℃**、热点 **68.5℃**
——与配置的初始工况一致，说明参数是从真实运行点反推的，不是拍脑袋填的。

**时间压缩**：Demo 需要在几十秒内看到热过程，因此在物模型里**显式声明** `time_compression = 300`，
把 τ_oil 从 9000s 压到 30s、τ_winding 从 600s 压到 2s。压缩倍数写进配置并随推流下发，不是隐藏的魔法系数。

**积分方式**：用指数积分的解析解 `θ ← θ + (θ∞ − θ)(1 − e^(−dt/τ))`，而不是显式欧拉。
任意步长下都稳定、无过冲——测试用例 `test_step_never_overshoots_steady_state_even_with_huge_dt` 专门验证这点。

**故障即边界条件**：注入"主变过热"不是改温度，而是把冷却器可用率降到 0.5（冷却器全停），
由模型自行把稳态油温推到 **91.3℃** 并越过 85℃ 危险阈值。改造前硬编码的 91.5℃ 现在是**算出来的**。

### 3.2 站内简化潮流模型

三条硬约束（也是单元测试的断言来源）：

1. **功率守恒**：Σ 各主变承担负荷 = 站内实际供电负荷（实测误差 0.000 MVA）
2. **电流由功率导出**：`I = S / (√3 · U)`，任何支路电流都不是独立随机数（实测误差 ≤ 0.02 A）
3. **失电即零流**：未带电的母线与支路电流恒为 0，全站功率为 0

拓扑（单电源终端站）：

```
            220kV I 段母线 ──[gis-202 母联]── 220kV II 段母线
                  │                                │
   [gis-201 进线] │                                │
   ◄── 电网 ──────┘                          trans-2 (240MVA)
                  │                                │
              trans-1 (240MVA)                     │
                  └────────── 110kV 母线 ──────────┘
                                 │
                        [gis-101 出线] ──► 负荷（占全站 37%）
```

负荷按**容量比例**分配给所有"高压侧带电"的主变，母联断路器只输送两侧的不平衡功率。由此得到三个真实行为：

| 操作 | 模型给出的后果 |
| :--- | :--- |
| 分闸 **gis-202**（母联） | II 段母线失电 → trans-2 退出 → 其负荷**转移**给 trans-1 → trans-1 负载率 76%→**151.9%** 过载，全站供电维持 364 MVA |
| 分闸 **gis-201**（进线） | 全站失压 → 所有支路电流归零、全站功率 0、`de_energized = true` |
| 分闸 **gis-101**（出线） | 只甩掉该出线的 37% 份额（约 135 MVA），主变负载率同步下降 |

### 3.3 保护逻辑与告警

- **过流保护**：定值来自物模型（出线 1000A，220kV 进线/母联 4800A），连续越限 `protection_delay_steps`（3 个采样周期）后出口跳闸，并生成"保护动作"操作票。
  > 这里踩过一个真实的坑：进线与出线共用类型模板时，进线误继承了 1200A 定值，导致出线过载时**进线也一起跳闸、全站失压**。修法是保护定值改为按设备配置——这正是"物模型分层"要解决的问题。
- **SF6 气压闭锁**：气压 < 0.45MPa 时拒绝合闸（HTTP 409），并产生"操作闭锁"告警。
  > 另一个坑：闭锁校验原本在"开关位置未变化"的短路返回**之后**，导致对已合闸开关重复下发合闸指令可以绕过闭锁。已修正为先校验后短路。
- **告警边沿触发**：仅当"告警等级或越限测点"发生变化时产生新告警。改造前 danger 级告警每步都发，150 步刷 150 条；现在是 3 条（冷却器预警 → 油温 75℃ 预警 → 油温 85℃ 危险）。

### 3.4 健康度模型

`health = 100 − Σ 惩罚项`，惩罚项全部来自模型量：油温超 75℃、热点超 95℃、负载率超 90%、
局放、振动、SF6 压力偏差、微水、触头磨损、动作次数。两台同型号主变因局放与振动不同而得分不同。

## 4. 数据流与写入纪律

```
                 ┌──────────────── TwinEngine（唯一状态源）────────────────┐
                 │  demand 随机波动 → 潮流求解 → 热路积分 → 保护判断 → 告警判定 │
                 └───────────────────────────┬────────────────────────────┘
                                             │ step() 每 1.5s
      ┌──────────────┬───────────────┬───────┴────────┬──────────────┐
      ▼              ▼               ▼                ▼              ▼
 WebSocket 广播   OPC UA 节点同步   MQTT 上报   事件落库(告警/操作票)  时序落库(每10步)
```

- **单一写入者**：只有 `ws.telemetry_background_publisher` 往数据库写；REST 路由只改引擎状态。
  这样避免了"路由写一次、推流又写一次"的重复记录，时序列也天然对齐同一个时间步。
- **OPC UA 地址空间由物模型生成**：17 个节点 / 5 个设备文件夹，断路器位置为可写节点。
- **老库平滑升级**：`init_schema()` 用 `PRAGMA table_info` 检查后 `ALTER TABLE ADD COLUMN`，幂等补列（已验证第二次执行为空）。

## 6. 仍然没有做的（诚实边界）

说清楚这些，比把它们包装成"已完成"更有说服力：

1. **没有真实物理实体**。数据源是仿真引擎（负荷需求是唯一的随机源），OPC UA 服务端也是自建的。
   按成熟度划分，这是**数字模型 → 数字影子之间**，不是严格意义的数字孪生。
2. **OPC UA 只有单向写入**。引擎快照会写入节点，但外部客户端直接改写节点值不会回流到引擎
   （且会被下一次同步覆盖）。真正入站的控制通路是 MQTT 控制主题。补节点轮询比对与写入仲裁即可闭合。
3. **没有状态估计**。真实系统要用电网状态估计器/量测冗余来校准模型，这里假设量测等于真值。
4. **热模型是单体质点模型**，没有分接头、油流回路、环境温度日周期、日照与风冷的耦合。
5. **潮流是简化模型**，只做拓扑与容量分配，没有阻抗矩阵、无功电压、N-1 潮流迭代。
6. **时序仍存 SQLite**。生产应换 TDengine/InfluxDB 并做降采样与冷热分层；当前落库是计数器抽样而非按时间切片。
7. **物模型是单文件**，没有版本管理、变更审批与多站/多租户隔离。
8. **无鉴权、无 CI、无容器化**。
